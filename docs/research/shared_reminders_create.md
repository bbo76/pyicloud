# Shared Reminders create: fail-closed CloudKit route

The old `RemindersService.create()` delegates to `RemindersWriteAPI.create()`, whose `modify` and subsequent lookup always use the private CloudKit client and `Reminders` zone. A list ID alone does not identify the database, zone, owner, or write permission. A successful shared read is not a write grant.

For each create, discover the list again from private and shared zone changes. The shared route comes from `/shared/zones/list` and a matching `/shared/changes/zone` envelope. Reject missing, duplicate, or contradictory list routes. In the shared zone, look up the exact `List`; it must expose a `share` reference pointing to the same zone and owner. Look up that exact `cloudKit.share` record in that zone. Only its own `currentUserParticipant.permission == READ_WRITE` and `acceptanceStatus == ACCEPTED` allow the shared `records/modify` request. Reject missing or contradictory metadata, per-record errors, and unsupported shared subtasks. The write and hydration lookup both use the shared client and exact zone/owner; neither retries privately. Private creates still use the private client and `Reminders` zone after list discovery.

Apple's [Record Dictionary](https://developer.apple.com/library/archive/documentation/DataManagement/Conceptual/CloudKitWebServicesReference/Types.html) documents `currentUserParticipant` on a share record. [Records lookup](https://developer.apple.com/library/archive/documentation/DataManagement/Conceptual/CloudKitWebServicesReference/LookupRecords.html) accepts `zoneID` in the request but does not guarantee it on every returned `List`. A prior sanitized shared-list lookup lacked both `zoneID` and `currentUserParticipant` on the parsed `List`; the parser retains them when synthetically present. Consequently this implementation does **not** infer permission from either the list itself or its readable zone. See parent diagnostic task `t_789cd2d6` for the cumulative synthetic evidence.

**Live limit:** the actual Reminders list-to-share association and accessibility of its share record have not been confirmed in an authorized, sanitized live read. Synthetic tests prove only the conditional route and rejection logic, not Apple's private Reminders response shape or that a live shared create will succeed. If the share reference or permission source is absent, the operation fails before any modify. Network uncertainty after a modify is not a safe reason to retry; read the target list before any further action to prevent duplicates.
